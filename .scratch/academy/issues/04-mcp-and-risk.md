# 04 · MCP 与风险边界

Type: grilling
Status: resolved
Blocked by: 01, 02

## 问题

MCP server 是可执行程序（stdio / http）。`05 票` 写死「自定义 tool 代码不开放（jiti 任意代码执行兜不住）」，`07 票` 说「MCP 白名单」但**至今没实现**——`engine/policy.mjs` 只挡了 `git clean`。

学院要不要管 MCP？管到什么程度？

## Answer

**MCP 归用户，应用不背书。**

- 学院可以装 / 下发 MCP 配置，但**不设白名单、不审查、不拦截**；
- 用户装什么 MCP、它干什么，**用户自负审查责任**（写进 `GLOSSARY.md`）；
- 应用只做两件事：**标来源**（本机目录 / 远端源 / 手写）+ **首次下发确认一次**（说明「这是可执行程序，由你自己担保」）；
- **自定义 tool 代码仍不开放**：MCP 是「配置 + 用户自带的外部程序」，tool 是「应用要帮你加载并执行任意 JS」——两件事，边界不动。

密钥仍按 Neo 的既有约束：`mcp.yaml` 里只许 `env:VAR`，不落明文。

## 为什么

- 白名单在 v1 是纯负担：一个人自用，白名单等于自己给自己发许可证，还会在一个你想用的 MCP 上卡住。而 07 票的白名单从来没实现过，说明它本来也没被需要。
- 但「不审查」不等于「不告诉」：来源标记是事后唯一能查的线索，成本一行 UI。
- 把 MCP 和 tool 分开，是为了不让「放开 MCP」顺手把 05 票否决的东西从后门放进来。

## 代价（接受）

- 没有兜底：一个恶意 MCP 在员工跑任务时会以该员工的权限执行。这被明确接受（自用产品 + 用户自负责任）。
- 「首次确认」要能**按资源 + 来源**记一次，否则每次招聘都弹。

## 被否掉的

- 白名单：与「自用」和「自负审查」直接矛盾，且实现成本高于收益。
- 全开（MCP + 自定义 tool）：tool 代码加载会引入任意 JS 执行，05 票否决过，没有新理由推翻。
