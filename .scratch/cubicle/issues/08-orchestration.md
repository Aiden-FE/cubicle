# 08 — 编排模型：发现 / 规划 / 执行 / 验收

Type: grilling
Status: resolved
Blocked by: 02, 06

## Question

「按预定的编排流程自动化的发现、规划、解决任务」具体指什么？编排的主体是**用户画的流程**、**内置 playbook**，还是**经理 agent 自主拆解**？v1 的最小可用形态是哪个？

## 四个动作分别要定义

- **发现**：任务从哪来？用户下达 / 监控仓库或收件箱 / 定时巡检 / 员工自己觉得该做？
- **规划**：谁把目标拆成任务？拆到多细？拆完谁分配？
- **执行**：员工领任务后是自主跑完，还是每步汇报？
- **验收**：谁判断做完了？失败了谁重试、谁升级？

## 关键分叉：Marvis 走了另一条路

Marvis 的做法是**一个对话框 + 主 Agent 自动拆解派活，不要求用户画流程**，只有定时任务作为补充。你说的「按预定的编排流程」听起来更像**可预设、可复用的流程模板**。

这两条路的产品含义完全不同：

- **自主拆解派**：上手快、显得聪明，但不可预测，出错难解释，用户不知道它下一步要干嘛。
- **预设流程派**：可预期、可复用、可审计，但用户要学一套编排语言，且覆盖不了长尾。
- **混合**：内置几条 playbook（如「修 bug」「写文档」），用户选模板，经理 agent 在模板内拆解。

这张票要选定一条，并说清 v1 走哪条、v2 再怎么演化。

## v1 的现实

v1 只有单员工，「编排」可能退化成一个**任务模板 + 一次规划调用**。但数据模型和 UI 必须给多员工留位。

## 要产出

编排的三层职责划分、v1 形态（含一个具体例子：从一句需求到一个可执行任务列表）、与多员工协作的接口约定、什么留给 v2。

## Answer

**结论：混合编排 —— playbook 库 + 一句话自动套；任务来源做成可插拔「来源适配器」（v1 内置人工工单）；规划 = 规划调用给结构化工单 + agent 步骤清单（展示性字段，不建子任务实体）；执行自主跑到完成 + steer 即时插话。**

### 1. 编排主体：playbook 库 + 一句话自动套

- **playbook = 可读的预设编排**，不是流程图：目标模板 / 验收标准模板 / 约束 / 步骤提示 / 角色建议 / 适用工作区类型。
- v1 内置 3 条：**「加功能」「修 bug」「写文档」**，外加「自由工单」兜底。
- 一句话下达 → 自动匹配 playbook（也可手选）→ 打开确认卡（回显目标与验收标准，可改）→ 建工单。经理 agent 在**模板内**拆解，不自由发挥。
- 不做画布：当同一 playbook 被复用多次且用户想固化时，v1.5 再考虑「把一条成功路径存成新 playbook」，仍不是 DAG。

### 2. 四个动作的 v1 定义

**发现（来源适配器）**

- v1 内置唯一来源：**人工工单**（俗称工单 = Task 的下达态，无独立实体）。
- 来源接口：`task.origin = { source_id, ext_ref?, scheduled? }`；v2 挂新来源不迁移数据。
- v2 示例（用户点名）：**Jira 来源** —— 定时 JQL 轮询，命中条件的新 Jira → 自动建工单（closed 状态同步回写可后置）。
- v1 不做：仓库监控、收件箱巡检、Webhook。

**规划**

- 两步：(a) 工单创建时的**规划调用**（轻量 LLM，非员工会话）：把一句话 → 结构化目标 + 验收标准 + 约束；(b) 员工开工时把 step_plan（步骤清单）写进任务的**展示性字段**，侧边栏时间线逐项打勾。
- **不生成子任务实体**。v2 多员工时把步骤升级为可分配的 Task（扩展位见 16 票）。

**执行**

- 员工自主跑到完成；失败 = failed + 人话原因（重试 = 会话追加）。
- **steer 插话即时生效**：插进正在跑的会话（pi / Claude / Qoder 的机制都支持，适配层归一）。

**验收**

- 06 票已定：通过 / 打回（同任务迭代）/ 取消。

### 3. 例子（demo 同款）

「给项目加一个把任务导出成 CSV 的功能，要有测试」
→ 命中「加功能」playbook → 确认卡：目标 / 验收（测试绿 + `todo export` 产物合法）/ 约束（不 tap 新依赖）
→ 建工单（origin: manual）→ 指派 owner 阿码 → 阿码开工 → step_plan：①读懂现有 CLI 结构 ②add export 子命令 ③写三条测试 ④自验后 commit → 侧边栏时间线展示、跑完后「待验收」。

### 4. 衔接

- 上下班 / 下班（13 票）作用于会话层，不清空工单队列。
- 多员工协作（经理角色、子任务升级、消息路由、文件冲突、走位触发）→ 新票 16。
- playbook 与角色的关系（哪些角色能领哪类工单）→ 16 票顺带，v1 不限。
