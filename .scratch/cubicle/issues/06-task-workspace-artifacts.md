# 06 — 任务执行、工作区与产出

Type: grilling
Status: resolved
Blocked by: 02

## Question

员工在**哪个目录**干活？任务的工作区是项目组共享还是员工私有？产出（文件、diff、文档）如何被记录、预览、验收？任务的状态机长什么样？

## 要拆清楚

- **工作区**：一个项目组一个目录？一个任务一个 git worktree？员工有私有 scratch 目录吗？
- **隔离**：两个员工同时改同一个仓库怎么办（worktree / 分支 / 锁）？v1 只有一个人，但模型要留位。
- **状态机**：待办 → 进行中 → 待验收 → 完成 / 失败 / 阻塞，还缺什么状态？谁能改状态？（「下班暂停 / 上班续跑」这两个态的确切语义由 13 票定，落在这里）
- **产出**：文件快照、diff、文档、截图、日志 —— 哪些进「产出」？存在哪？怎么预览？
- **验收**：用户点通过？还是另一个员工审？v1 要不要「验收」这一步？
- **失败**：任务卡住 / 循环 / 超时，怎么判定与重试？

## 要产出

工作区模型、任务状态机图、产出模型、验收流程、失败与重试策略。

## 参考

Marvis 的任务侧边栏：步骤、当前由谁执行、中间结果、产出文件/网页预览。这是我们「产出」的最小参照。

## Answer

**结论：git 仓库是工作区真相；任务开工记起点 HEAD，产出 = 相对起点的四件套；git commit 由员工自主完成，应用对 git 全程只读；任务五态 + 正交暂停标志；验收保留，「打回」= 同任务追加迭代会话。**

### 1. 工作区模型

- ProjectGroup 绑定一个 `workspaceRoot` = 本地 git 仓库根目录（v1 硬要求 git；非 git 目录允许试用但无 diff / 回滚能力，界面上标警示）。
- 任务开始时应用记录**起点 HEAD**（只读操作，供 diff 与追溯）。
- 员工没有独立 scratch 目录：会话、日志都在应用私有目录（03 票的隔离原则），不和工作区混。

### 2. git 责任边界（本票最重要的一拍）

- **员工自主 commit**（用户拍板：「依赖人就不叫数字员工了」）。何时 commit、message 怎么写，属于「git 工作流」能力约定，内置在角色技能里（→ 05 票）。
- 应用对 git **只读**：记起点、读 diff、读 status。**不代打 commit，也不做破坏性回滚。**
- 回滚也是派任务：「撤销你上一个提交」让员工自己来 —— 与自主原则一致。
- push / reset --hard / branch 等高危动作的风险分级 → 07 票（默认倾向：commit 必须可、push 默认禁、reset 破坏性禁）。

### 3. 任务状态机（v1）

`待办 → 进行中 → 待验收 → 完成 / 失败`，外加**正交的「暂停」运行时标志**（下班 / 预算暂停共用，语义 13 票）。

- 状态推进以系统事件为主：跑完 → 自动「待验收」。
- 用户三键：**通过**（→ 完成）、**打回**（同任务追加迭代会话，意见文本进入下一轮）、**取消**。
- 员工不改状态机；重试与打回都不新开任务（历史连续），只有彻底重来才新开任务。

### 4. 产出四件套

| 条目 | 内容 | 存放 |
|---|---|---|
| diff 摘要 | 相对起点 HEAD 的文件数 / ±行数 | 应用私有 artifacts |
| 变更文件清单 | 单文件可预览 | 内容真相在工作区；清单与预览快照存应用侧 |
| 测试 / 命令输出 | 关键 bash 调用 stdout 尾部 | 应用私有 artifacts |
| 收尾报告 | agent 最后一条完整文本 | 应用私有 artifacts |

原则：**文件内容的真相永远在工作区**；应用侧存的是摘要、副本与日志（会话 JSONL 指针），工作区被清理也能回看「当时发生了什么」。

### 5. 验收

- 保留「待验收」拍点（也是 01 剧本 2:20 的信任镜头）。
- 「通过」→ 完成。**没有应用侧一键 commit**：员工已完成自己的提交，侧边栏显示「员工已提交 a1b2c3」。
- 「打回」→ 同任务追加迭代会话：历史一条线，迭代轮次可数。

### 6. 交接

- 「git 工作流」技能（何时 commit / message 规范 / 不主动 push）→ 05 票的预设角色表
- 暂停标志（下班 / 预算）的进入退出语义 → 13 票
- git 高危动作分级与沙箱 → 07 票
- 侧边栏 UI → 10 票
