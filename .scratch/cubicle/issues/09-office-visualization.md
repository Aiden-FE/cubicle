# 09 — 办公室可视化与动画驱动

Type: prototype
Status: resolved
Blocked by: —

## Question

v1 的办公室长什么样、有哪些状态动画、动画如何被 agent 事件驱动？

## 已知

- 风格参考腾讯 Marvis：**3D 白模办公室 + 2D 扁平角色 + 斜俯视（30–40°）娃娃屋**，不是纯 2D 等距。
- 技术底座已定：PixiJS 8 + spritesheet + 自研网格 A\* / 状态机，Tiled 做等距地图。
- 要演出的状态（你的描述 + Marvis 已验证的集合）：coding、写文档、做表格、摸鱼玩手机、扫雷、喝咖啡、走动、走到对方工位沟通；Marvis 还有打盹冒 z、健身、离岗。**07 票新增：被拦**（策略拒绝 → 气泡）；**13 票新增：下班暂停 / 上班激活**的表现。
- v1 只有单员工，但动画系统要按多员工设计。

## 必须先定的视觉路线

「参考 Marvis」和「用 PixiJS」之间存在真实张力，三条路：

- **A. 纯 2D 等距**（Tiled 地图 + spritesheet）：最省事、性能最好，但和 Marvis 的「娃娃屋」质感有差距。
- **B. 预渲染 3D 背景 + 2D 角色合成**（Blender 出等距底图/序列帧，PixiJS 贴角色）：最接近 Marvis，资产管线重，但换布局要重渲染。
- **C. 实时 3D**（Three.js 场景 + 2D 角色）：最灵活，但与 PixiJS 选型冲突，复杂度和性能都上一个台阶。

这张票要顺带把这条路线定下来，并给出「为什么另外两条不选」。

## 要产出

1. **一版可点的视觉原型**（办公室 + 若干工位 + 1 个角色 + 4 个状态切换），用来定风格与信息密度。
2. **状态清单与优先级**：每个状态的触发条件、可被打断性、动画时长。
3. **事件映射表**：agent 的哪个事件 → 哪个动画（`tool_execution_start` 写文件 → 敲代码？读文件 → 看屏幕？`turn_end` → 回到 idle？）。
4. **资产规格**：spritesheet 尺寸 / 帧率 / 朝向数、工位与家具的图层规范、换装怎么留口。
5. **头顶信息设计**：Marvis 在工位上方悬浮名牌 + 任务气泡 + token 计数。我们要显示什么？

## 输入

- [Marvis 拆解](../research/marvis-teardown.md)（含状态动画清单与视觉细节）。
- [桌面技术选型](../research/desktop-stack.md)。

## Answer

**结论：视觉路线 = A「娃娃屋」构图（用户拍板）+ 场景层实现 = B「预渲染 3D 背景（分层）+ 2D 扁平角色」（2026-11-05 二次拍板，取代纯 2.5D 矢量）；C 对照组被否决（办公室即主视图）。**

> ⚠️ 修订说明：初版 Answer 写的是「矢量伪 2.5D」；用户在 11 票追问「PixiJS 做不了 Marvis 的 3D」后确认：**PixiJS 是 2D 渲染器，但娃娃屋构图不需要真 3D** —— 质感靠 Blender 预渲染的 3D 背景分层贴图 + 2D 角色合成实现。2.5D 矢量降为 fallback（无美术资源时的占位方案），原型里的矢量画法即 fallback 的验证。

### 1. 原型与验证

- 原型文件：[prototypes/09-office-prototype.html](../prototypes/09-office-prototype.html)（throwaway，勿提交进主干；真实实现时从这里移植）。
- 已在浏览器实跑验证：33 秒任务演示全程推进（读/写/测试失败/**被拦拍点**/**请示暂停+批准按钮**/咖啡走位/待验收抽屉），空闲时每 9 秒摸鱼。
- 首版曾因残留 `WS()` 未定义函数卡在第一帧（用户反馈「未见演示动画」）→ 已修复并逐帧截图复核。

### 2. 状态清单与优先级（打断规则）

| 优先级 | 状态 | 进入条件 | 可被打断 |
|---|---|---|---|
| 0（最高） | **被拦**（07） | 策略拒绝事件 | 否，播完 0.7s 抖动 |
| 1 | **请示等待**（07） | agent 输出请示 | 否，直到 steer 批复 |
| 2 | **下班暂停**（13） | 公司下班 | 否 |
| 3 | **任务活动**（读/写/跑/思考） | 归一化工具事件 | 任何更高优先级 |
| 4 | **走位**（去茶水间 / 回工位 / 未来走别人工位） | 空闲窗口或转交事件 | 可被 0-2 打断 |
| 5（最低） | **闲时**（摸鱼 / 咖啡 / 发呆——02 票三动作） | 空闲 > 9s 的窗口 | 可被一切打断 |

- 原则：**动画永远服从真相**——没有事件时宁站桩呼吸，不许假装敲键盘。

### 3. 事件 → 动画映射表（消费 14 祧归一化事件）

| 引擎事件（归一化） | 动画状态 | 屏幕画面 | 气泡 |
|---|---|---|---|
| `turn_start` / `message_update`(思考) | code（打字节拍慢） | 编辑器空行 | 「思考中…」 |
| `toolcall` read/grep | read | 代码滚动 | 「正在读 <file>」 |
| `toolcall` write/edit | code（敲击快） | diff 高亮滚动 | 「正在写 <file>」 |
| `toolcall` bash | term | 终端逐行 | 命令首行 |
| `tool_result` 失败 | term 红 | FAIL 行 | 「跑测试… n failed」 |
| `tool_result` 成功(测试) | term 绿 | PASS 行 | 「n passed ✅」 |
| `policy_deny`（07） | **被拦** | 屏幕定格 + 角色红框抖 | 红气泡：被拦原因 |
| agent 请示 | **请示** | 定格 | 蓝气泡 + 「批准/先不」内联按钮 |
| `turn_end` | code→idle | 画面渐暗 | 「已提交 a1b2c3」 |
| `agent_end` | review | 显示器显示 diff 摘要屏 | 「待验收」 |
| 会话暂停（13） | idle + 屏幕熄 | 显示器转场熄灭 | 「zZ 已暂停」 |
| 空闲 > 9s | **闲时** | 屏幕熄 | 「摸鱼中…」 |
| 空闲 > 45s | 起身去茶水间（咖啡）→ 回 | 终端熄屏 | ☕ |

### 4. 头顶信息（名牌 + 气泡）

- 名牌：`名字 · 角色` + 第二行 `状态 · token`（原型已定，对齐 Marvis）。
- 气泡是「解释层」的主通道：读什么、写什么、为什么停，全部经由气泡说人话。
- **密度细则（默认已按原型落定，可在 10 票里一票否决）**：名牌常显；气泡最多同屏 1 个；不建议叠加更多（颜色已够）。

### 5. 资产规格（初稿，给美术资产管线雾）

- **场景层 = 预渲染分层（2026-11-05 定）**：Blender 出斜俯视娃娃屋，按 **back / mid / front-occluder 三层**导出（WebP/PNG，2x 与 1x），PixiJS 把角色插在 mid 与 front 之间 → 才有「走到桌后」的正确遮挡。换布局 = 重渲染（已接受）。
- 角色：2D 扁平矢量为基（黑色身形 + 白眼圈 + 彩围巾区分角色，红=程序员），高约 44–52px；朝向 3-4 个（娃娃屋斜视）；状态机驱动切换；spritesheet 帧率 8–12fps。
- 名牌与气泡：Canvas/Pixi 矢量绘制（原型路径），避免 DOM 开销。
- 「会呼吸」的主角升级（眨眼 / 头发）留 spine-pixi 接口，不进 v1 硬需求。
- **渲染抽象**：场景层必须走可替换接口 `SceneRenderer`（drawFloor / drawFurniture / drawCharacter / hitTest），渲染技术不写死进业务代码 —— 便于 B → C（Three.js）或回退 A 的迁移。

## Comments

- 2026-11-05：用户反馈首版原型「未见演示动画」→ 定位为脚本残留未定义函数致 rAF 停摆；修复后在 agent 浏览器逐帧截图验证通过。视觉路线用户拍板 A；名牌密度与「被拦→请示」拍点按原型默认记录（留票否决）。
- 2026-11-05 澄清（用户追问「PixiJS 不是做不了 Marvis 那种 3D 俯视吗」）：**属实 —— PixiJS 8 是 2D 渲染器，没有 3D 场景图/透视相机/实时光照**。但路线 A 的「娃娃屋」不依赖真 3D：Marvis 的质感来源是构图 + 暖白光 + 软阴影，09 原型即用 **Canvas 2D 矢量伪造 2.5D**（地板梯形、家具双面、模糊阴影）。差距：镜头推移、真实遮挡、实时光照做不到或需预渲染。落地路径三条：**A 纯 2.5D 矢量（v1 推荐）** / **B 预渲染 3D 背景 + 2D 角色（美术升级路径，换布局需重渲染）** / **C Three.js 场景层（真 3D，v2 探索）**。架构要求：场景层抽象为可替换的 `SceneRenderer` 接口（drawFloor / drawFurniture / drawCharacter / hitTest），**渲染技术不写死在业务代码里**。
